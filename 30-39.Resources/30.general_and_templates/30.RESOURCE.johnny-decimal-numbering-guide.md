# Johnny Decimal Numbering Guide

Johnny Decimal is a general-purpose numbering system for organizing folders and files so that any item's location can be inferred from its number alone, and so the tree never gets more than about 10 items deep at any one level. This guide explains how it's applied in this vault. (The method itself is a publicly documented general-purpose system, not specific to any one person's setup — see johnnydecimal.com for the original write-up.)

## The core idea

1. Pick no more than 10 broad **categories** (top-level ranges). Each gets a two-digit range: `00-09`, `10-19`, `20-29`, and so on up to `90-99`.
2. Inside each category, break it into no more than 10 **areas** (subfolders). Each area gets a single number from that category's range, using the range's tens digit as the shared prefix.
3. If a subfolder needs further breakdown, repeat the same "max ~10 items" rule one level deeper.

The result: given any number, you can say immediately which category it belongs to, without needing to remember an index.

## This vault's categories

| Range | Category | What lives here |
|---|---|---|
| `00-09` | Inbox | Anything not yet sorted |
| `10-19` | Projects | Time-bound work with a defined finish line |
| `20-29` | Areas | Ongoing responsibilities with no finish line |
| `30-39` | Resources | Reference material, guides, standards (this file lives here) |
| `40-49` | Archives | Inactive projects and areas kept for the record |

Ranges `50-99` are left open on purpose — add a new category only when an existing one genuinely doesn't fit, following the same "two-digit range + short label" pattern.

## Example: how `10-19.Projects/` breaks down

```
10-19.Projects/
  10.general_and_templates/   ← the "1" prefix ties every subfolder back to the 10-19 range
  11.active_projects/
  12.on_hold_projects/
  13.finished_projects/
```

Every subfolder inside `10-19.Projects/` starts with `1`, because `1` is the tens digit of `10-19`. This is what makes the numbering self-describing: see a folder named `12.on_hold_projects/` anywhere in the vault (even out of context) and you know instantly it belongs under the Projects category, specifically the "on hold" bucket.

The same pattern repeats for `20-29.Areas/` (subfolders start with `2`), `30-39.Resources/` (subfolders start with `3`), and so on.

## Numbering individual files

Within an active subfolder, individual project/area files also carry a number — usually just the subfolder's number, since most people don't have more than a handful of active items at once (see "Naming conventions" in `AI_INSTRUCTIONS.md`). If you regularly have many active projects and want each to have its own stable number, you can extend the pattern one level further (e.g., `11.01`, `11.02`, …) — but most personal and small-business vaults never need this; don't add complexity you don't have a use for yet.

## Why this beats an unstructured tag-only system

- **Stability:** a folder's number doesn't change when you rename its label, so links and file paths saved elsewhere (in daily notes, in other tools) don't break.
- **No decision fatigue:** "where does this go?" has one obviously-correct answer — the range that matches its PARA category — instead of an open-ended choice.
- **Scales down as well as up:** an almost-empty vault with one project still has an unambiguous place for it; a vault with fifty projects still keeps each folder to a scannable size.

## When to break the pattern

Two intentional exceptions exist in this vault, both explained where they're used:

- **Daily notes** (`Daily_notes/YYYY-MM-DD.md`) are dated, not numbered — a date is already a stable, sortable identifier.
- **Goal notes** (`.GOAL.` files) live at the vault root, prefixed by time period instead of folder number, because a single goal often spans multiple PARA categories at once (see `AI_INSTRUCTIONS.md` § "File naming conventions").

Everything else follows the numbering rule above.
