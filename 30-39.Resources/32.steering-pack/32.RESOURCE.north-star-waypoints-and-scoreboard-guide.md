# North Star, Waypoints, and the Weekly Scoreboard

> How the **Steering Pack** module adds a slower, numbers-aware layer on top of the base weekly review and GOAL work streams. See `MODULES.md` at the repository root for what else this module includes.

## The problem this solves

A quarterly `.GOAL.` note and a weekly review can both look healthy — tasks checked off, work streams progressing — while the underlying multi-year direction quietly drifts, because neither one is built to look further than a quarter or a week ahead. This module adds two small tools that close that gap without adding a whole new planning system: a place to write down the multi-year destination once (North Star + Waypoints), and a five-minute weekly numbers check-in (the scoreboard) that asks whether anything actually moved toward it.

## The three altitudes

| Note type | Time horizon | Question it answers |
|---|---|---|
| `.NORTHSTAR.` (this module) | Multi-year | "What does 'this worked' look like, eventually?" |
| `.GOAL.` (base) | One quarter | "What matters most right now?" |
| Weekly review / scoreboard | One week | "Did anything actually move?" |

None of these replace the others. A GOAL file's work streams are still where you sequence this quarter's projects; the North Star just gives those quarters something to add up to.

## How the pieces connect

1. Write ONE `.NORTHSTAR.` note (template `13`) with 2–4 Waypoints — long-horizon checkpoints, not tasks. Worked example: `[[2026-2027.NORTHSTAR.grow-brightline-studio-into-a-full-time-business]]`.
2. Any `.PRJ.` or `.AREA.` note can add a `Serves: "W1"` frontmatter field declaring which Waypoint it's working toward. Worked example: `[[10-19.Projects/11.active_projects/11.PRJ.launch-styled-recipe-shot-list-product]]`.
3. Run `scripts/serves_mapping_report.py --vault-root .` any time you want to see which Waypoints have active work pointed at them, and which don't. It reads every `.NORTHSTAR.` note for Waypoint definitions and every `.PRJ.`/`.AREA.` note for `Serves:` fields — no configuration needed beyond pointing it at your vault root (see the portability note in `scripts/serves_mapping_report.py`'s own docstring).
4. Fill in a weekly scoreboard (template `14`) alongside your normal weekly review — its `## Waypoint progress` section is exactly where the serves-mapping report's findings become a one-line human judgment call ("closer," "unchanged," "slipped").

## Example output

Running the script against this repository's own fictional worked examples produces:

```
$ python3 scripts/serves_mapping_report.py --vault-root .

# Serves-Mapping Report

North Star notes scanned: 1 · Waypoints found: 3 · Project/Area notes scanned: 5

## Coverage by Waypoint

### W1 — First productized revenue stream live
_Defined in `2026-2027.NORTHSTAR.grow-brightline-studio-into-a-full-time-business.md`_
- `10-19.Projects/11.active_projects/11.PRJ.launch-styled-recipe-shot-list-product.md`

### W2 — Productized revenue reaches parity with one month of client work
_Defined in `2026-2027.NORTHSTAR.grow-brightline-studio-into-a-full-time-business.md`_
- (nothing currently serves this Waypoint)

### W3 — Full transition option exists
_Defined in `2026-2027.NORTHSTAR.grow-brightline-studio-into-a-full-time-business.md`_
- (nothing currently serves this Waypoint)

## Not serving any Waypoint

_Not automatically a problem — plenty of maintenance work doesn't need to serve a Waypoint. Shown for visibility, not as a to-do list._

- `10-19.Projects/11.active_projects/11.PRJ.launch-cooking-blog.md`
- `10-19.Projects/11.active_projects/11.PRJ.refresh-portfolio-website.md`
- `20-29.Areas/21.active_areas/21.AREA.client-bookkeeping.md`
- `20-29.Areas/21.active_areas/21.AREA.ideas-inventory.md`
```

Reading this: W2 and W3 having nothing pointed at them yet is expected and correct at this early stage — W1 hasn't even been reached. The four "not serving any Waypoint" notes are the studio's existing client-service work, which is fine — not every project needs to serve the North Star, only the ones that are meant to be moving it.

## Notes on using this pattern

- **Don't force `Serves::` onto everything.** Routine maintenance (bookkeeping, an ongoing client relationship) has no obligation to serve a Waypoint. The report's "not serving any Waypoint" section is informational, never a checklist to clear to zero.
- A `Serves:` field pointing at a Waypoint ID that no longer exists (renamed or removed) shows up as a warning in the report rather than failing silently — fix the reference or update the field.
- Re-run the script whenever you fill in a weekly scoreboard — it's the fastest way to fill in that scoreboard's `## Waypoint progress` section honestly instead of from memory.
