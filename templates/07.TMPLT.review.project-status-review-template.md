# Template: Project Status Review

> A dated snapshot of a single project's health, written periodically (weekly or biweekly for active projects, less often for slow-moving ones). Where a Weekly Review scans *everything* briefly, a Project Status Review goes deep on *one* project.

## What this template is for

Some projects are simple enough that the `## Notes` section of the Project note is all the history you need. Others — especially ones with a client, a deadline, or several moving parts — benefit from a dated series of status snapshots you can look back through to see how the project actually progressed (not just what's true right now). Use this template when a project is important or complex enough to justify that history.

## Required frontmatter fields

```yaml
---
Type: "Project Status Review"
Date: "<YYYY-MM-DD>"
Reviewing: "<link to the project this reviews>"
---
```

## Required sections

1. `## Status at a glance` — one line: on track, at risk, or blocked, plus why in a few words.
2. `## Progress since last review` — what actually moved since the previous status review (or since the project started, for the first one).
3. `## Risks and open questions` — anything that could knock the project off its target date, and anything still undecided.
4. `## Next milestone` — the next concrete thing that needs to happen, and roughly when.

## Notes on using this template

- Status review files live **alongside the project they review**, in the same active-projects subfolder, using the project's folder number and the `.STATUSREVIEW.` type marker plus the date: `<number>.STATUSREVIEW.<YYYY-MM-DD>.<short-description>.md`. This keeps a project's whole history in one place instead of scattering it.
- Not every project needs this. A two-week solo task doesn't need a formal status review; a six-week client project with a deadline usually does. Use judgment — if you're not sure, start the project without one and add the first status review the first time you feel like you've lost track of where things stand.
- **This is a snapshot, not a to-do list.** Don't duplicate the project's `## Todo` section here — link to it (`[[project-file#Todo]]`) instead of copying tasks across two files that can then drift out of sync.
- A run of consecutive "at risk" or "blocked" status reviews without the underlying cause changing is a strong signal to reassess the project's scope or deadline, not just note the same risk again.
